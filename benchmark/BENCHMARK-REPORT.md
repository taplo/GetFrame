# GetFrame 视频抽帧性能测试报告

**测试日期**: 2026-05-31
**测试工具**: `benchmark/run.py`
**测试组件版本**: getframe-worker v0.1.0

---

## 测试环境

| 项目 | 配置 |
|------|------|
| **CPU** | Intel Xeon E5-2680 @ 2.70GHz (16 核) |
| **内存** | ~15 GiB |
| **OS** | Ubuntu 26.04 LTS |
| **Docker** | v29.5.2 |
| **FFmpeg** | libavcodec59 (容器内) |
| **存储** | MinIO (S3)，同一主机 |
| **消息队列** | Kafka (同一主机) |
| **数据库** | MySQL 8.0 (同一主机) |

---

## 测试方法

- 使用 `ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate={fps}` 生成合成测试视频
- 通过 RTSP 推流到 MediaMTX，worker 从 MediaMTX 拉流解码
- 每路流为 1080P H.264，目标抽帧率分别为 5fps 和 1fps
- 每轮测试包含 30s 稳定期 + 6 次采样（间隔 5s），取稳定后数据
- 为避免堆间干扰，每轮测试在不同的 stream count 间重启完整 docker compose 栈

## 分析

### 1. 低帧率（1fps）：编码不再为瓶颈（libjpeg-turbo）

- **线性扩展到 32 流**: actual_fps 随流数线性增长（1→19.7），无显著吞吐天花板
- **CPU 每流约 4-5%（1-16 流）**: 编码开销从旧的 12% 降至 4%，降幅 ~65%
- **24+ 流的瓶颈为 S3/Kafka I/O**: CPU/流从 4% 降至 2%，吞吐稳定在 ~19fps
- **32 流仅用 72% CPU**: 16 核服务器轻松承载 32 路，仍有 28% CPU 裕量

### 2. 高帧率（5fps）：解码仍为瓶颈，但范围扩展

#### 线性区（1-8 流）
- 每流稳定 ~6fps（超目标 20%），**每流 CPU ~19%**（旧版 55-78%，节省 ~65%）
- 总 CPU 1-8 流从 55%→179%（远低于旧版的 55%→620%）

#### 扩展区（12-16 流）
- **libjpeg-turbo 将 CPU 饱和点从 12 流推迟到 ~16 流**
- 12 流总 CPU 282%（旧版 970%），每流 FPS 5.6（旧版 4.8）
- 16 流总 CPU 415%（旧版 989%），吞吐 **86 fps**（旧版 53 fps，提升 63%）

#### 瓶颈转移区（24-32 流）
- 总 CPU 稳定在 460%（16 核的 29%），**不再是 CPU 瓶颈**
- 吞吐在 77-85 fps 稳定，**比旧版翻倍**（旧版因 CPU 饱和仅 37-45 fps）
- **瓶颈推测**: S3 上传 IO + Kafka 发布延迟

### 3. 跨场景综合对比

| 场景 | 最大吞吐（旧） | 最大吞吐（新） | 提升 | CPU 节省（每流） |
|:---:|:-----------:|:-----------:|:---:|:--------------:|
| 1fps | ~18 fps | ~19.7 fps | +9% | -65% |
| 5fps | ~53 fps | **~86 fps** | **+62%** | -65% |

> libjpeg-turbo 在高帧率场景效果更显著，因为释放的 CPU 被大量帧的解码流水线重新利用。

## 建议容量规划

| 场景 | 旧版建议 | 新版建议 | 瓶颈 |
|:----:|:-------:|:-------:|:----:|
| 5fps 抽帧 | **~12 路** | **~16 路** | CPU（解码） |
| 1fps 抽帧 | **~24 路** | **32+ 路** | I/O（存储/消息） |

> libjpeg-turbo 将 JPEG 编码效率提升约 3 倍，1fps 场景的瓶颈已从编码转移到 S3/Kafka I/O，
> 建议每 16 核承载 32+ 路 1fps 或 ~16 路 5fps 抽帧流。
> 高帧率场景的解码仍为 CPU 瓶颈，优化方向应为 GPU 硬解。

### 扩展方向

1. **GPU 解码 / QSV**：将 H.264 解码卸载到硬件，可大幅提升每核密度
2. **异步 S3 上传批处理**：减少小文件上传的 per-request 开销
3. **Kafka 生产者批处理优化**：增加 `batch.size` / `linger.ms`
4. **NUMA 感知调度**：避免跨内存域访问
